# Deployment

Sunfall Arc deployment centers on the Start request boundary:
`createRequestHandler(app, { server, implementations })`, which returns an
Effect-returning handler. `app` is the `App.define(...)` definition the
browser entry also launches; `implementations` are the server bodies of its
served Resources and Actions (and any server functions); `server` is the
server Layer, which must provide every service the app's root and those
implementations need, so a correctly typed handler has no requirements left
for the host. Each host shape has exactly one import path:

- `@sunfall/arc-start/fetch` for Fetch-style hosts (Workers, edge runtimes,
  Bun, Deno, tests);
- `@sunfall/arc-start/node` for Node HTTP (`IncomingMessage` /
  `ServerResponse`).

Each subpath exposes one Effect-first adapter plus one host-shaped facade for
platforms whose contract is already fixed. `StartRequestHandlerError` is
exported from the `@sunfall/arc-start` root.

## Production Build (Node)

`vite build` with `sunfallArcStart` builds a server-rendered app for
production, unless the app prerenders (`prerender`, a static site). It runs
two Vite environments:

- the client, into `dist/client`, from `clientEntry` (default
  `/src/main.tsx`) or the app's own `build.rolldownOptions.input`, with
  Vite's manifest;
- the server, into `dist/server`: the app's `serverEntry` and
  `dist/server/index.js`, generated by Start.

```sh
vite build
PORT=3000 node dist/server/index.js
```

Every Start build (prerendered sites too) names the chunks the entry loads:
`vendor-*.js` holds its dependencies (Arc, Effect, Solid, and the other
packages it imports), `app-*.js` the app modules that the entry and lazy
routes share. A package that only lazy routes import stays in their chunks.

`dist/server/index.js` serves the client build's files (hashed `assets/` with
`immutable` caching, `public/` files with `no-cache`) and sends every other
request to the server entry's handler (its `default` or `handleRequest`
export, or `handlerExport`; the build fails if the entry exports none of
them). Documents reference the built entry and its
stylesheets, and `modulepreload` the entry, its imports, and the matched
route's lazy `*.component.tsx` chunk, so the browser fetches the route's code
alongside the entry instead of after it runs. It listens on `PORT` (default 3000) and `HOST`, and closes gracefully on `SIGINT`/`SIGTERM`. If it cannot start, it prints a `StartNodeServeError` naming the client build or the address (for example, that the port is already in use) and exits with status 1.

That file calls `serveMain(handler, { clientDir, assets })` from
`@sunfall/arc-start/node`. A host that manages its own process uses `serve`,
the same server as a scoped Effect that yields the listening `http.Server`.
Under `vite dev` and in tests, documents reference the source entry, which
Vite serves.

## Fetch And Edge-Style Hosts

Use `toFetchHandler` when the host integration can run Effects itself:

```ts
import { createRequestHandler } from "@sunfall/arc-start";
import { toFetchHandler } from "@sunfall/arc-start/fetch";
import { app } from "./app-definition.js";
import { AppServerLive, implementations } from "./app.server.js";

const fetchHandler = toFetchHandler(
  createRequestHandler(app, { server: AppServerLive, implementations }),
);
```

Use `createFetchHandler` when the host itself expects
`(request: Request) => Promise<Response>`:

```ts
import { createRequestHandler } from "@sunfall/arc-start";
import { createFetchHandler } from "@sunfall/arc-start/fetch";
import { app } from "./app-definition.js";
import { AppServerLive, implementations } from "./app.server.js";

const fetch = createFetchHandler(
  createRequestHandler(app, { server: AppServerLive, implementations }),
);

export default {
  fetch,
};
```

## Node HTTP

Use `createNodeServerHandler` for the ordinary `node:http` callback shape:

```ts
import { createServer } from "node:http";
import { createRequestHandler } from "@sunfall/arc-start";
import { createNodeServerHandler } from "@sunfall/arc-start/node";
import { app } from "./app-definition.js";
import { AppServerLive, implementations } from "./app.server.js";

const handler = createNodeServerHandler(
  createRequestHandler(app, { server: AppServerLive, implementations }),
);

createServer(handler).listen(3000);
```

`trustForwardedHeaders` defaults to `false`: the request origin comes from the
`Host` header (or `origin` when you pass a fixed public origin). Set
`trustForwardedHeaders: true` only behind a proxy that overwrites
`x-forwarded-proto` and `x-forwarded-host`; otherwise clients could spoof the
origin your app sees.

`createNodeHandler` is the Effect-first Node adapter for hosts that want to run,
fork, or recover the Effect program themselves.

The Node adapter is covered for:

- untrusted-by-default and explicitly trusted forwarded origin handling through
  `trustForwardedHeaders`;
- request bodies for non-`GET`/`HEAD` methods;
- bodyless `HEAD` responses;
- streaming Web `Response` bodies through Node backpressure;
- preserving multiple `Set-Cookie` headers.

## Platform Recipes

Cloudflare Workers, Vercel Edge, Netlify Edge, and other Fetch-native hosts
that require a Promise-shaped exported `fetch` function use `createFetchHandler`
as shown above. Bun's HTTP server uses the same boundary:

```ts
import { createRequestHandler } from "@sunfall/arc-start";
import { createFetchHandler } from "@sunfall/arc-start/fetch";
import { app } from "./app-definition.js";
import { AppServerLive, implementations } from "./app.server.js";

const fetch = createFetchHandler(
  createRequestHandler(app, { server: AppServerLive, implementations }),
);

Bun.serve({
  fetch,
});
```

Vercel and Netlify Node functions use `@sunfall/arc-start/node` when the host
provides Node `IncomingMessage`/`ServerResponse` values, and
`@sunfall/arc-start/fetch` for their edge runtimes.

Every host serves the implementations through the same handler, at two fixed
paths: `POST /__sunfall-arc/rpc` for Resource loads and server functions (an
`effect/rpc` `RpcServer` with JSON serialization, answering one request per
POST) and `POST /__sunfall-arc/action` for Actions (JSON only). Route both
to the Start handler, along with page requests: a form-encoded or multipart
`POST` to a page is a no-JavaScript Action submission the handler answers
(a redirect, or the page rendered again), so page routes must forward `POST`
as well as `GET`. There is nothing else to mount. Responses from the RPC path are always `200` JSON
arrays of `effect/rpc` messages (typed failures and defects travel inside
them), so proxies should not rewrite or cache that path. The browser reaches
both through the client Layer's `HttpClient` (else `FetchHttpClient`) on the
page's origin.

Static hosts can prerender routes during the production Vite build:

```ts
import { sunfallArcStart } from "@sunfall/arc-start/vite";

export default defineConfig({
  plugins: [
    sunfallArcStart({
      serverEntry: "/src/server.tsx",
      prerender: {
        autoStaticPathsDiscovery: true,
        autoSubfolderIndex: true,
        crawlLinks: true,
      },
    }),
  ],
});
```

Static file routes are discovered automatically when they have no path params.
Dynamic routes stay explicit: add concrete paths through `prerender.pages` or
link to them from a discovered page when `crawlLinks` is enabled. The build
writes ordinary HTML files into Vite's output directory, using
`/page/index.html` paths by default.

Prerendering calls the server entry's handler in-process through a temporary
Vite server, then swaps the page's dev entry script and dev stylesheets for the
built entry chunk and its CSS from Vite's build manifest. The plugin turns on
`build.manifest` (a string `build.manifest` path is respected), so
`dist/.vite/manifest.json` ships with the build.

Prerendering also writes the app's not-found page to `404.html` at the output
root: it renders an unmatched URL through the same handler, so the page is
whatever the app's router renders when no route matches (a 404 response is
expected and written). GitHub Pages, Netlify, Cloudflare Pages, and Vercel
serve that file for every missing URL. Its asset and link URLs are absolute
under Vite's `base`, so it works at any depth, such as
`/repository-name/docs/missing/page` on a GitHub Pages project site. The
browser hydrates it as the not-found page whatever the URL, even one a dynamic
route matches but that has no prerendered page, and in-app links then
navigate client-side. A client navigation whose target page answers 404
settles on the not-found page too. To keep a different file, add an explicit
page with `outputPath: "404.html"`; to skip it, return `false` from `filter`
for the page whose `source` is `"not-found"`. Outside a prerender, Start
answers every unmatched URL with status 404 and the same not-found render.

For a fully static deployment, set
`buildPolicy.staticClient: { target: "static" }`. With `forbidBrowserRpc`
(default `true`), the browser build compiles the `RpcClient` out of
`App.launch`, so the browser never calls a served Resource's load: every
value it renders comes from a prerendered page. The first page hydrates from
its own payload, and client navigation through
`makeStartStaticHistoryAdapter` fetches the target's prerendered page and
hydrates the Resources its preload loaded before the route renders. The docs
site is the example: its recipes are served Resources (`Resource.define`
without `load`, implemented with `Resource.implement` in a `*.server.ts`
module), which run in-process while prerendering and over RPC only in dev
(`examples/docs-site/src/start-options.ts`). Set `forbidBrowserRpc: false` to
keep the RPC client in a static build whose host also serves the RPC path.

## Current Limits

- There are no host-specific packages for Cloudflare, Vercel, Netlify, Bun, or
  static hosts; the `./fetch` and `./node` subpaths plus the recipes above
  cover them.
- Static prerendering is built into the Start Vite plugin. Host-specific static
  packages can still add deploy-provider details later.
- Framework package manifests are publishable public scoped packages versioned
  `0.1.0-alpha.1`, with package keywords and repository/homepage/bugs metadata
  pointing at `https://github.com/sunfall-labs/arc`.

The `runtime` option of `createFetchHandler` / `createNodeServerHandler` exists
only for handlers that still have requirements (for example a route preload
service the server Layer does not provide); the types require it exactly then.

Keep deployment integrations as small wrappers over `createRequestHandler(app, ...)`
and the tested adapters above.
